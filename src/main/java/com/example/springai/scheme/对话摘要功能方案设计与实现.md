# 对话摘要功能方案设计与实现

## 1. 背景与问题

`ChatController.chatStreamWithContext` 方法在多轮对话场景下，会将 Redis 中存储的全部历史消息打包发送给 AI 模型。随着对话轮数增加，存在以下问题：

- **token 超限风险**：历史消息越来越多，可能超出模型的 context window 限制，导致 API 报错
- **成本线性增长**：每次请求都会消耗与历史消息量成正比的 token 数
- **单条消息无限制**：如果某条消息内容特别长（如贴代码、文档），会进一步加剧上述问题

## 2. 方案设计

### 2.1 核心思路

在每次用户发消息时，检查会话消息总数。当新消息积累超过阈值时，调用 AI 模型对早期消息生成摘要，存入 Redis 元数据。构建模型上下文时，组合 **"摘要 + 最近 N 条消息"** 发送给模型。

这样既保留了早期对话的关键语义信息，又有效控制了发送给模型的 token 数量。

### 2.2 存储设计

复用现有的 `conversation:{sessionId}:meta` Redis Hash 结构，新增两个字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `summary` | String | AI 生成的摘要文本 |
| `lastSummarizedCount` | String (int) | 上次摘要时的消息总数，用于判断是否需要重新生成 |

不新增 Redis Key，与现有元数据（createdAt、lastActiveAt、messageCount、userId）共存。

### 2.3 摘要触发条件

```
messageCount > MAX_CONTEXT_MESSAGES  且  (messageCount - lastSummarizedCount) >= MAX_CONTEXT_MESSAGES
```

其中 `MAX_CONTEXT_MESSAGES = 20`（10 轮 x 每轮 2 条）。

含义：消息总数超过 20 条，且距上次摘要已积累 20 条新消息时，才重新生成摘要。避免每次请求都调用模型生成摘要，控制额外的 API 调用开销。

### 2.4 模型上下文构建

发送给模型的消息列表结构如下：

```
[system 消息: 摘要]  <- 如果有摘要
[最近 20 条历史消息]  <- 来自 Redis List
[当前用户消息]        <- 本轮用户输入
```

摘要以 `role=system` 的消息插入到消息列表最前面，让模型在理解上下文的同时不受早期消息的 token 消耗影响。

### 2.5 流程图

```
用户发送消息
    |
    v
保存用户消息到 Redis
    |
    v
获取 messageCount 和 lastSummarizedCount
    |
    v
需要生成摘要？ --否--> 读取已有摘要（可能为 null）
    |是
    v
获取全部历史消息
    |
    v
调用 AI 模型生成摘要
    |
    v
保存摘要到 Redis meta
    |
    v
获取最近 20 条历史消息
    |
    v
构建上下文：摘要 + 最近消息 + 当前消息
    |
    v
调用流式接口返回响应
```

## 3. 实现过程

### 3.1 ConversationService -- 新增摘要存储方法

**文件**: `src/main/java/com/example/springai/service/ConversationService.java`

新增 3 个方法，均基于现有的 `getMetaData()` 和 Redis Hash 操作：

**`getSummary(String sessionId)`**
- 从 meta Hash 中读取 `summary` 字段
- 不存在时返回 null

**`saveSummary(String sessionId, String summary, int messageCount)`**
- 将摘要文本写入 meta Hash 的 `summary` 字段
- 将当前消息总数写入 `lastSummarizedCount` 字段
- 用于后续判断是否需要重新生成摘要

**`getLastSummarizedCount(String sessionId)`**
- 从 meta Hash 中读取 `lastSummarizedCount` 字段
- 未生成过摘要时返回 0

同时，之前已实现的 `getMessages(String sessionId, int limit)` 重载方法也服务于本功能，用于获取最近 N 条消息。

### 3.2 ChatService -- 新增摘要生成方法

**文件**: `src/main/java/com/example/springai/service/ChatService.java`

**`summarizeMessages(List<MessageDTO> messages)`**
- 将消息列表格式化为可读文本（`用户: ...` / `助手: ...`）
- 优先使用 `originalContent`（Markdown 原文）作为内容
- 构建摘要 prompt：要求模型在 200 字以内保留关键信息、用户需求和重要结论
- 复用已有的 `chatSimple()` 方法调用模型，无需额外的 HTTP 客户端

**`chatStreamWithContext` 方法修改**
- 新增 `String summary` 参数
- 非空时，在消息列表最前面插入 `role=system` 的摘要消息
- 其余逻辑不变

### 3.3 ChatController -- 集成摘要逻辑

**文件**: `src/main/java/com/example/springai/controller/ChatController.java`

在 `chatStreamWithContext` 方法中，保存用户消息之后、获取历史消息之前，插入摘要逻辑：

1. 通过 `getMetaData()` 获取当前消息总数 `messageCount`
2. 通过 `getLastSummarizedCount()` 获取上次摘要基准数
3. 判断触发条件：`messageCount > 20 && (messageCount - lastSummarizedCount) >= 20`
4. 触发时：获取全部消息 -> 调用 `summarizeMessages()` -> `saveSummary()` 存入 Redis
5. 未触发时：通过 `getSummary()` 读取已有摘要
6. 获取最近 20 条历史消息，连同摘要一起传给 `chatStreamWithContext`

## 4. 涉及文件清单

| 文件 | 变更类型 | 变更内容 |
|---|---|---|
| `ConversationService.java` | 新增方法 | `getSummary`、`saveSummary`、`getLastSummarizedCount` |
| `ChatService.java` | 新增方法 + 修改方法 | 新增 `summarizeMessages`；`chatStreamWithContext` 增加 `summary` 参数 |
| `ChatController.java` | 修改方法 | `chatStreamWithContext` 中集成摘要触发和上下文构建逻辑 |

## 5. 测试验证

1. 启动应用：`mvn spring-boot:run`
2. 登录后创建会话，连续发送超过 10 轮对话（20 条消息以上）
3. 检查 Redis 中 `conversation:{sessionId}:meta` 是否包含 `summary` 和 `lastSummarizedCount` 字段
4. 继续发送消息，确认后续请求的上下文中包含摘要（可通过日志观察）
5. 验证摘要每积累 20 条新消息后会重新生成
